# Phase 2 — P2300R10 wording-zone validation

**Status:** Phase 2 complete (200 sentences labeled, sids 1500..1699).
The wording zone is the formal C++ specification text proposed for
inclusion in the standard: definitions of execution resources,
asynchronous operations, senders, receivers, schedulers, queries;
type-system propositions; `*Mandates:*` clauses.

## What we expected vs. what we found

**Expected:** the wording zone is boilerplate / should be SKIPped
en masse (this was the working hypothesis going into Phase 2).

**Found:** the wording zone is the **claim-densest region of the
paper**. Phase 2 gold:

| class | n | % |
| --- | --: | --: |
| TARGET | 155 | 77.5% |
| CONTEXT | 11 | 5.5% |
| SKIP | 34 | 17.0% |

vs. Phase 1 (prose zone): 44% TARGET / 53% CONTEXT / 3% SKIP.
vs. P4003R3 (mixed prose): 47% TARGET / 37% CONTEXT / 16% SKIP.

The formal definitions are **exactly** what the paper proposes to
add to the standard — they are extractable claims, just expressed
in dense formal language ("An asynchronous operation is a distinct
unit of program execution that...", "A sender is a factory for one
or more asynchronous operations.").

The 34 SKIPs are NOT boilerplate — they're **pysbd fragmentation
artifacts**:

| pattern | count |
| --- | --: |
| number-only sentences (`"1."`, `"2."`, ...) | 19 |
| ellipsis-prefix continuations (`"... is explicitly created."`) | 10 |
| ≤2-word fragments | 2 |
| `[*Example: ... -- *end example*]` blocks | 2 |
| other (`"Otherwise, X."` continuations, broken expressions) | 1 |

These exist because pysbd is splitting numbered-list spec sentences
of the form

> An async op is a distinct unit ... that: 1. is explicitly created.
> 2. can be explicitly started once at most. 3. once started,
> eventually completes ...

into pieces like `"1."`, `"... is explicitly created."`, `"2."`,
`"... can be explicitly started ..."`. Each piece becomes a
"sentence" the classifier has to deal with.

## What the classifier does with Phase 2

Baseline (`"A statement of fact or opinion."`):

| margin | acc | T→S | T→C | TARGET recall | SKIP recall |
| --- | --: | --: | --: | --: | --: |
| (0.05, 0.4) | 0.410 | 1 | 77 | 78/155 (50%) | 0/34 |
| (0.05, 0.6) | 0.410 | 0 | 78 | 77/155 (50%) | 0/34 |
| (0.0, 0.4)  | 0.555 | 1 | 46 | 109/155 (70%) | 0/34 |

Two devastating findings:

1. **50% TARGET recall.** Half the formal definitions don't fire.
2. **0% SKIP recall.** Of the 34 fragmented-pysbd-output SKIPs, zero
   are correctly tagged.

Why 0% SKIP recall? Inspecting the broken-fragment SKIPs:

```
sid=1517 t=0.991 s=0.990  text="1."
sid=1518 t=0.994 s=0.949  text="... is explicitly created."
sid=1519 t=0.988 s=0.984  text="2."
sid=1527 t=0.991 s=0.988  text="4."
```

The classifier scores TARGET ≈ 0.99 AND SKIP ≈ 0.99 on both,
because there's no semantic content to distinguish. The diff is
~0.001, falls into CONTEXT by default. This is **not a classifier-
tuning problem** — these sentences shouldn't be sent to the
classifier at all.

## Alt-hypothesis on Phase 2

Same three TARGET hypotheses we tested earlier, on the wording zone:

| TARGET hypothesis | acc | T→S | TARGET recall | SKIP recall |
| --- | --: | --: | --: | --: |
| `"A statement of fact or opinion."` (baseline) | 0.410 | 0 | 77/155 (50%) | 0/34 |
| `"A statement about software behavior, design, or specification."` | 0.575 | 2 | 114/155 (74%) | 0/34 |
| `"A statement describing what something does, is, or proposes."` | **0.745** | **0** | **149/155 (96%)** | 0/34 |

The winning hypothesis from Phase 1 cross-validates a third time:

- P4003R3 (mixed prose, 137 sentences): **97% TARGET recall, 0 T→S**
- P2300R10 Phase 1 (tutorial prose, 210 sentences): **98% TARGET recall, 0 T→S**
- P2300R10 Phase 2 (formal wording, 200 sentences): **96% TARGET recall, 0 T→S**

The hypothesis travels well across radically different paper styles
and zones within the same paper. No ensemble involved; nli-small
alone.

## Structural pre-filter (the SKIP recovery)

The 33 broken-fragment SKIPs the classifier cannot tell apart from
TARGETs match a tiny set of deterministic regexes. Tested on **both**
phases:

| pattern | Phase 2 catches | Phase 2 false-positives |
| --- | --: | --: |
| `^\s*\d+\.\s*$` (number-only) | 19 SKIPs | 0 |
| `^\s*\.{2,}\s` (ellipsis-prefix) | 10 SKIPs | 0 |
| length-after-strip < 3 words | 2 SKIPs | 1 TARGET ("query(get_allocator))`.") |
| `^[\W\d]+$` (all-punct/digit) | (subset of above) | 0 |
| `[*Example: ... -- *end example*]` | 2 SKIPs | 0 |

Combined coverage: **33/34 Phase 2 SKIPs caught**. The single missed
SKIP (sid=1500, `"Otherwise, \`make_exception_ptr(err)\`."`) is a
genuine prose fragment without a list-marker or ellipsis tell.

Phase 1 false-positive check: **1 sentence** (sid=160,
`"The \`inline_scheduler\`:"`) would be filtered as too-short. I'd
labeled it CONTEXT; it's a list-header anyway, SKIP-ish.

Net effect of adding the pre-filter to the production pipeline:

- Drops ~33 truly junk fragments per wording-heavy paper before
  classification.
- Keeps the classifier's input distribution closer to "real prose,"
  which is what zero-shot NLI handles well.
- Costs ~1 occasional borderline-CONTEXT-sentence false-skip per 200
  sentences. The downstream LLM still sees the chunk surrounding
  this sentence, so this is recoverable noise rather than lost
  signal.

## Other observations on Phase 2

- **Chunker overlap duplicates 80+ sentences** in this region
  (sids 1591..1670 are exact duplicates of 1511..1590). The chunker
  is producing overlapping windows so spec definitions appear twice.
  This is benign for classification (we tag both copies the same)
  but doubles the classifier's work and the LLM's reading load.
  Worth a follow-up: detect and dedupe at chunk-boundary time.
- **Pysbd segmentation is failing** on numbered-list spec text. A
  custom regex-based pre-merge (rejoin `"1."` + `"... text"` back
  into one sentence) would eliminate the fragment SKIPs entirely
  and recover the lost claim content. The pre-filter is a band-aid;
  the proper fix is at the segmentation layer.
- **Cross-references with `[basic.def.odr]`-style brackets are
  preserved as TARGETs** correctly — the alt hypothesis doesn't get
  fooled by them.

## What this changes about the design

Two new recommendations, on top of the hypothesis change from
Phase 1:

1. **Add a structural pre-filter in `_decompose_sentences`** that
   auto-SKIPs the 5 patterns above. Keeps the classifier's job
   focused on real prose.
2. **Consider rejoining number+continuation fragments** in a
   preprocessor before pysbd. This is a follow-up; the pre-filter
   handles the symptom adequately for now.

The hypothesis change alone is the cheapest ship (one line). The
pre-filter is the next-cheapest (~10 lines of regex). Together they
fix the two largest classifier failure modes observed across the
study, with no ensemble, no new model, no extra compute.
